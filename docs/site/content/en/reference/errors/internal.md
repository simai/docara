# Internal errors

Docara checks not only the project but also itself: that its own component
descriptions, templates and intermediate build data agree. These checks do
not depend on the page text or settings; if such an error appears, the cause
is not in your project.

## What to do

1. Run a full build again: `docara build <environment>`. Sometimes an
   interrupted earlier build causes the error.
2. Check that Docara is installed completely and not changed by hand:
   `composer install` restores the package files from `composer.lock`.
3. If the error repeats, report it in the
   [Docara repository](https://github.com/simai/docara/issues). Attach the
   code, the output of `docara doctor --json` and, if possible, the page on
   which the build stopped. Do not attach passwords or tokens.

Do not work around the error by editing the build result: the next build
replaces it.

## Internal check codes

### Page parsing

The intermediate representation of a page that Docara builds before output.

| Code | What is checked |
| --- | --- |
| `DOCUMENT_AST_EMPTY`, `DOCUMENT_AST_INVALID`, `DOCUMENT_IR_EMPTY`, `DOCUMENT_INPUT_INVALID` | The page is parsed into a non-empty valid structure |
| `DOCUMENT_IR_SOURCE_LOCATION_INVALID`, `DOCUMENT_IR_SOURCE_NODE_TYPE_INVALID`, `DOCUMENT_SOURCE_SPAN_INVALID` | Every block has an exact place in the source file |
| `DOCUMENT_HEADING_INVALID`, `DOCUMENT_LINK_INVALID`, `DOCUMENT_MARKDOWN_NODE_INVALID` | Headings, links and plain Markdown are parsed without loss |
| `DOCUMENT_IR_COMPONENT_NODE_INVALID`, `DOCUMENT_IR_COMPONENT_BLOCK_NODE_INVALID`, `DOCUMENT_IR_CONTAINER_NODE_INVALID`, `DOCUMENT_COMPONENT_RENDERER_NODE_INVALID`, `DOCUMENT_COMPONENT_BLOCK_RENDERER_NODE_INVALID` | Blocks and components are passed to output in the expected form |
| `DOCUMENT_SMART_CALL_NODE_INVALID`, `DOCUMENT_SMART_COMPONENT_NODE_INVALID`, `DOCUMENT_SMART_COMPONENT_ORDINAL_INVALID`, `DOCUMENT_SMART_VIEW_INVALID` | Smart component calls are numbered and passed to output whole |
| `DOCUMENT_CONTAINER_CONTRACT_MISSING`, `DOCUMENT_CONTAINER_ORDER_INVALID`, `DOCUMENT_CONTAINER_SLOT_INVALID`, `DOCUMENT_CONTAINER_DEPTH_SEMANTICS_INVALID`, `DOCUMENT_CONTAINER_RENDERER_INVALID`, `DOCUMENT_CONTAINER_RENDERER_UNSUPPORTED`, `DOCUMENT_CONTAINER_CHILD_ARTIFACTS_REQUIRED` | The surface, grid and card have a full description of nesting |
| `DOCUMENT_IR_RENDERER_UNKNOWN`, `DOCUMENT_IR_RENDERER_DUPLICATE` | Every block kind has exactly one way of output |
| `DOCUMENT_OUTLINE_PARSE_FAILED`, `DOCUMENT_OUTLINE_SERIALIZE_FAILED` | The outline is built from the finished page |

## Marks of passed checks

`docara doctor`, `docara validate` and their `--json` output also list the
checks that passed, with the status `pass`. These are not errors: there is
nothing to fix.

| Code | What passed the check |
| --- | --- |
| `PROJECT_CONFIG_VALID` | The project settings |
| `SCHEMA_CATALOG_VALID` | The catalogue of settings schemas |
| `SMART_REGISTRY_VALID`, `DESIGN_REGISTRY_VALID`, `BINDING_REGISTRY_VALID` | The lists of Smart components, design descriptions and bindings; their count is shown beside them |
| `DESIGN_ARTIFACT_VALID` | One design description |
| `PAGE_MARKDOWN_VALID` | The Markdown of one page |
| `DOCUMENTATION_SOURCES_VALID`, `DOCUMENTATION_SOURCE_VALID` | Documentation tracking sources: all of them and one |
| `PROJECT_REGISTRIES_VALID` | All project registries together; the number of components and design descriptions is shown beside it |
| `COMPOSITION_EXPANDED`, `SAFE_VIEW_TREE_VALIDATED` | The page frame is assembled from regions, and its tree passed the tag and attribute check |
| `AUTHOR_EXECUTABLE_SURFACES` | With the status `absent`: the page settings have no templates or code |
