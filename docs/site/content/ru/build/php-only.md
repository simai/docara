# Сборка сайта

Для сборки нужны PHP 8.2+, Composer и Node.js 20+. PHP читает Markdown и
настройки, Node.js запускает среду выполнения Composition Recipe, а Docara
записывает готовые HTML-страницы. Закреплённая поставка SIMAI Framework входит
в пакет Docara, поэтому отдельная копия Framework не нужна.

```bash
php vendor/bin/docara build local
php vendor/bin/docara build production
```

Если `node` отсутствует в `PATH`, задайте
`DOCARA_NODE_BINARY=/path/to/node`. Устанавливать npm-зависимости сайта не нужно.

Первый аргумент — имя окружения. По умолчанию используется `local`, а результат
пишется в прямой дочерний каталог `build_<environment>` внутри корня сайта.

Builder разрешает очистку только безопасного каталога `build` или
`build_*`. Символическая ссылка, выход из корня или пересечение с входными
файлами останавливают сборку до удаления существующего результата.

Для размещения готового сайта PHP, Composer и Node.js не нужны: веб-сервер
отдаёт HTML, CSS и JavaScript. Проектный PHP-код для обычного сайта не требуется.

## Обработка готовых страниц

`page_transforms` — команды, которые получают готовый сайт до того, как
Docara его измеряет: например, раскрашивают код во время сборки. Каждая
команда запускается в корне проекта, последним аргументом получает папку
сайта и меняет страницы на месте:

```json
{
  "page_transforms": [
    {"command": ["node", "scripts/highlight-code.mjs"]}
  ]
}
```

Команды выполняются по порядку, после записи страниц и до отчёта о
производительности и квитанции сборки, поэтому `verify-static` проверяет
страницы такими, какими их опубликовали. Ненулевой код выхода останавливает
сборку с `PORTABLE_PAGE_TRANSFORM_FAILED`. Страница, изменённая после сборки
вручную, по-прежнему не проходит проверку.

## Что лежит в готовом каталоге

Собранный каталог содержит HTML страниц, копии контентных ассетов и служебные
Framework-ассеты. Рядом с ним Docara кладёт квитанции сборки — они описывают,
как собран сайт, и не публикуются:

```text
build_production/                  публикуется целиком
  index.html
  404.html                         страница для отсутствующих адресов
  section/page/index.html
  _docara/search-index.json
  _docara/search.js
  _docara/docara-shell.<sha256>.css   общие стили первого кадра, несколько на страницу
  _docara/framework/
  _docara/vendor/simai-framework/runtime/<revision>/
  old/route/index.html
build_production.docara/           квитанции сборки, не публикуются
  resolved-page-plans.json
  redirects.json
  locale-routes.json
  performance.json
  examples.json
  …
```

Каталог `build_production/` можно копировать на хостинг как есть: служебных
файлов сборки в нём нет. Квитанции из `build_production.docara/` читают
`verify-static`, однострочная пересборка `build --page`, `preview` и `inspect`.
Сайт, собранный Docara 3.0.0, хранил их внутри результата в `.docara/`; такие
каталоги по-прежнему проверяются, но при новой сборке квитанции переезжают
наружу.

В `_docara/vendor/` попадает только то, чем пользуются собранные страницы.
Mermaid публикуется, если хотя бы одна страница содержит диаграмму, KaTeX со
шрифтами — если есть формула, начертания значков Rounded и Sharp — если
разметка, скрипт примера или собственные стили сайта запрашивают это
семейство, полный `utility.full.css` Framework — если страница на него
ссылается. Лицензия библиотеки публикуется вместе с ней. Подмножество значков,
каталог Outlined и полный шрифт Outlined публикуются всегда: значки вне
подмножества Smart компоненты выбирают уже в браузере. `verify-static` заново
вычисляет этот выбор по страницам и сообщает `@vendor-asset-selection`, если
нужного файла нет или он отличается от файла пакета.

Каталог значков в `_docara/vendor/docara/icon-catalog/` — статические копии
всех значков Material Symbols для каждого семейства (`outlined`, `rounded`,
`sharp`), толщины (`light`, `regular`, `medium`) и заливки. Каждая копия весит
около 0,3 МБ, и браузер скачивает только те, что нужны значкам страницы.
Обычная страница обходится подмножеством Outlined; страница со значками
Rounded, Sharp, другой толщиной или заливкой получает по одной копии на
каждое такое сочетание вместо полного шрифта на 3,5–5,3 МБ. Полный шрифт семейства загружается
только для значка с другой толщиной (например, `bold`), `grade` или
оптическим размером.

HTML можно обслуживать обычным статическим веб-сервером. Значение `base_url`
должно совпадать с префиксом размещения: `/` для корня домена или безопасный
путь вроде `/project/docs/` для вложенного размещения.

Файлы поиска появляются только когда `search.enabled: true` хотя бы для одной
страницы. Индекс строится до очистки destination, проходит JSON Schema и
содержит только URL опубликованных страниц, locale, заголовки, описания,
навигационный путь и видимый текст. Браузер загружает его лениво. Индекс и
runtime имеют независимые SHA-256 query revisions.

Проверка артефакта читает `base_url` из
`resolved-page-plans.json`: совпадающий deployment-префикс удаляется
перед поиском файла внутри build-каталога, а похожий или посторонний абсолютный
путь отклоняется.

Verifier требует exact schema manifest, непустой список страниц и точное
совпадение его `output` и redirect receipt со всеми HTML-файлами результата.
Отсутствующий, дублированный, лишний, symlink- или hardlink-output отклоняется.
Элемент HTML `<base>` запрещён, чтобы относительные quoted `href`/`src` всегда
разрешались одинаково verifier-ом и браузером.

`404.html` — страница «Страница не найдена» в оболочке сайта. Она есть в
`resolved-page-plans.json` с `"not_found": true`, все её адреса записаны от
корня сайта, и её нет в поисковом индексе, `sitemap.xml`, `llms.txt` и
`_docara/page-metadata.json`. Настройка и подключение на сервере описаны в
разделе [Размещение на хостинге](/build/hosting/#страница-404).

Если `redirects_file` не пуст, квитанция `redirects.json` фиксирует SHA-256
source, locale, версию документации, `base_url`, source/target URL и output
каждого redirect. Redirect HTML содержит canonical, `noindex`, meta refresh и
обычную видимую ссылку на один и тот же внутренний target.

Локальные ссылки с `#fragment` проверяются против фактических HTML `id` — как в
сыром Unicode, так и в percent-encoded форме. Основные диагностические маркеры:

| Маркер | Причина |
| --- | --- |
| `@duplicate-html-id` | На странице один `id` встречается больше одного раза |
| `@missing-fragment` | Локальная ссылка указывает на отсутствующий якорь |
| `@unsafe-fragment-encoding` | Fragment содержит неправильную percent-кодировку или невалидный UTF-8 |

Любой из этих маркеров делает проверку артефакта неуспешной.

Текущий lock публикует необходимые Docara файлы SIMAI Framework локально:
Core, используемые utilities, нужные Docara webpack/language chunks, Inter,
Material Symbols и допущенные Smart assets. Страница не зависит от
runtime-загрузки с CDN.

Перед первым отображением общий production Asset Planner SIMAI Framework
анализирует готовый HTML страницы по тем же правилам `distr/rule/rule.json`,
которые использует динамический Loader. Он раскрывает зависимости и подключает
точный набор CSS страницы и геометрию Docara в порядке каскада.

Эти CSS публикуются несколькими общими файлами `docara-shell.<sha256>.css`,
имя которых определяется содержимым. Когда собраны все страницы, Docara
группирует их исходные CSS в файлы, которые подходят сразу многим страницам:
большая общая часть — один файл для всего сайта, частые наборы компонентов —
свои файлы, редкие — небольшие отдельные. Страница подключает только нужные ей
CSS, ничего лишнего, в среднем 4–6 файлов вместо полусотни; браузер кеширует их
между страницами. Общий объём файлов ограничен двойным объёмом различных
исходных CSS сайта.

Каскад страницы не меняется. Файл — это точные байты его исходных CSS подряд.
Два исходных CSS меняются местами только тогда, когда порядок между ними не
может повлиять ни на одно объявление: у них нет общего свойства в одном слое
каскада (сокращённые записи, логические и физические свойства и префиксные
псевдонимы считаются одним свойством) и нет одноимённых `@keyframes`,
`@property`, `@font-face` и подобных правил. Порядок слоёв задаёт `core.css`
Framework, который подключается раньше. Всё, что анализ не понимает, остаётся
на своём месте.
Нужные JavaScript-модули подключаются в порядке зависимостей до Core, а
`window.SF_PRELOADED` перечисляет только фактически опубликованные ресурсы.
Поэтому Loader не загружает их повторно после первого отображения и остаётся
ответственным только за содержимое, появившееся позднее.

Docara является первым потребителем этого общего build-time механизма, а не
владельцем отдельного списка Framework-компонентов. Проект без production
планирования продолжает работать по прежней динамической схеме через `sfPath`,
`sfSmartPath`, `core.css` и `core.js`. Редкий ресурс первого кадра, который
невозможно увидеть в итоговом HTML, можно явно назвать через необязательный
`data-sf-require`.

Те же ранние ресурсы включают используемые подмножества Inter и Material
Symbols. Обычный fenced code-блок сразу получает серверный заголовок языка той
же геометрии, что и итоговая интерактивная панель копирования. Это не глобальный
скелетон: содержимое страницы доступно сразу, а поздняя регистрация компонентов
не меняет размеры каркаса и кодовых блоков.

Пока Inter загружается, Framework использует локальный метрически совместимый
fallback. Он сохраняет естественные размеры текста и элементов управления,
поэтому подмена шрифта не перестраивает шапку, меню и колонки. Фиксированная
высота шапки, скрытие страницы или отдельный проектный кеш для этого не нужны.

`resolved-page-plans.json` содержит отдельный Framework asset receipt
для каждого HTML-output: входные файлы и их SHA-256, порядок JavaScript, список
preload-модулей, hash HTML-содержимого и публичные имена generated CSS в
порядке подключения.
`verify-static` повторно вычисляет каждый план по финальному HTML и отклоняет
ложный preload, изменённый CSS, отсутствующий ресурс, stale receipt или другой
порядок подключения. В точном production-режиме `utility.full.css` не
публикуется.

На статическом хостинге рекомендуется разделить кеширование:

- файлы с SHA-256 в имени — `Cache-Control: public, max-age=31536000, immutable`;
- HTML — без `immutable`, с обычной проверкой актуальности (`ETag` или
  `Last-Modified`).

Это не
превращает произвольный upstream-компонент в поддерживаемый: admission
по-прежнему определяется manifest, provider policy и exact lock.

Публичную production или release готовность следует заявлять только после
отдельной приёмки конкретного артефакта и условий распространения.

### Что сборка сообщает о себе

Система показывает, что именно она собрала. Квитанция
`build_production.docara/resolved-page-plans.json` хранит эффективные
настройки каждой страницы и происхождение значений, а
`_docara/component-catalog.json` фиксирует набор компонентов, доступный в
конкретной сборке.

## Воспроизводимость

При одинаковых Markdown, JSON, Framework lock и версии генератора повторная
сборка должна создавать байт-в-байт одинаковый результат.

Docara не записывает в portable output текущую дату и абсолютные локальные
пути. `_docara/page-metadata.json` использует историю Git exact source, если она
доступна; в Composer dist без `.git` поля `updated_at`, `revision` и `author`
равны `null`. Время распаковки или изменения файла не попадает в публичный
результат. Для каждой страницы квитанция `build_production.docara/resolved-page-plans.json`
содержит:

- итоговую конфигурацию;
- упорядоченный trace входных файлов с SHA-256;
- provenance каждого значения;
- canonical hash плана;
- нормализованные вызовы компонентов;
- точный asset plan;
- output path и публичный URL.

Для проверки соберите сайт дважды в чистые каталоги и сравните хэши деревьев.
Изменение входа или lock должно объяснимо изменить соответствующий план.

Если поиск включён, `content_sha256` в `_docara/search-index.json` вычисляется
из canonical documents, а query revision `_docara/search.js` — из точных байтов
runtime. Поэтому изменение содержания и изменение поискового кода инвалидируют
кэш независимо и остаются воспроизводимыми.

CSS постоянного каркаса собирается из зафиксированных Framework-ресурсов и
`declarative-shell.css` и публикуется общими файлами
`docara-shell.<sha256>.css`; имя определяется точными байтами файла. Группировка
зависит только от наборов CSS всех страниц, поэтому одинаковая сборка получает
те же файлы. Framework shell receipt фиксирует для каждой страницы её исходные
CSS, подключаемые файлы и их порядок, предзагруженные модули и hash каждого
файла, а любое содержательное изменение даёт новое имя. Однострочная
пересборка `build --page` не трогает другие страницы: она использует
опубликованные файлы и добавляет новые только для изменившегося набора, а
полная сборка заново группирует весь сайт.

Если настроены redirects, квитанция `redirects.json` аналогично фиксирует
canonical records, SHA-256 канонически нормализованного source, locale, версию
документации и `base_url`. Форматирование и порядок записей во входном JSON не
меняют результат сборки.
