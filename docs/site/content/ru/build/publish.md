# Публикация и откат

Публикуйте только каталог, который прошёл `verify-static`. Инструкция не
зависит от конкретного хостинга: команды копирования и переключения замените
на принятые в вашей инфраструктуре.

## Подготовьте проверяемый пакет

«Готов к выпуску» не означает «уже опубликован». Из чистой рабочей копии на
точной ревизии соберите ZIP командой `scripts/build-release-package.php`, затем
проверьте парный `release-manifest.json` через
`scripts/verify-release-package.php`. Две независимые рабочие копии с
одинаковыми ревизией, версией и планируемым тегом должны дать побайтно
одинаковые ZIP, manifest и контрольную сумму.

Manifest записывает ревизию исходников, SHA-256 архива и каждого файла,
закреплённую версию SIMAI Framework, список владения файлами и перечень
компонентов (SBOM). В архиве нет Git, CI, тестов, рабочих отчётов,
локального кеша и учётных данных. Значение `published=false` обязательно до
отдельного решения о выпуске.

Перед обновлением сохраните проект и его `composer.lock`. Установите точный
ZIP, затем выполните `update --verify`, `update --dry-run` и только после
проверки операций — `update --apply`. Тексты, ассеты, `docara.json`, настройки
разделов и страниц и `lang.json` языков принадлежат проекту, и обновление их не
трогает. При ошибке выполните `update --rollback=<id>` и проверьте
восстановленные хеш файлов движка и lock-файл.

Остановите выпуск, если:

- не совпадает ревизия или хеш;
- владение файлами нарушено или неизвестно;
- план устарел или пакет для отката повреждён;
- зависимость не закреплена на точной версии;
- в сборке есть битая ссылка;
- не пройдена проверка в браузерах или безопасности;
- ZIP не повторяется во второй чистой рабочей копии.

## 1. Задайте адрес сайта

До сборки задайте `base_url` в `docara.json`:

```json
{
  "schema": "docara.site.v1",
  "preset": "docs",
  "framework_lock": "simai-framework.lock.json",
  "base_url": "/docs/"
}
```

Используйте `"/"` для корня домена и `"/docs/"` для подкаталога. Не исправляйте
ссылки вручную после сборки.

## 2. Соберите и проверьте

```bash
php vendor/bin/docara build production
php vendor/bin/docara verify-static build_production
```

Если команда завершилась с ненулевым кодом, остановите публикацию.

## 3. Запишите отпечаток каталога

Составьте список файлов проверенного каталога с их хешами. Например, в
окружении с `shasum`:

```bash
(
  cd build_production
  find . -type f -exec shasum -a 256 {} \; | LC_ALL=C sort
) > build_production.manifest.sha256
shasum -a 256 build_production.manifest.sha256
```

Храните этот список вместе с записями о выкладке, а не внутри публикуемого
каталога. Для исходного и проверочного каталогов используйте одну и ту же
команду подсчёта.

## 4. Скопируйте в новый проверочный каталог

Не перезаписывайте рабочий каталог на месте. Создайте новый каталог с версией
в имени, например:

```text
releases/2026-07-19T120000Z/
```

Скопируйте туда только содержимое `build_production`. Учётные данные
передавайте через средства доступа вашей инфраструктуры; не добавляйте их в
исходники Docara, историю команд, Markdown или собранный сайт.

После копирования составьте такой же список файлов для проверочного каталога
(staging) и сравните его с исходным. Несовпадение останавливает переключение.

## 5. Проверьте основное

До переключения, через проверочный адрес или локальную привязку, проверьте:

1. главная страница отвечает успешным HTTP-кодом;
2. вложенная страница открывается по своему адресу;
3. CSS, ассеты Framework, логотип и значок сайта загружаются без 404;
4. поиск находит известную страницу;
5. ссылка на заголовок `#…` прокручивает к нему;
6. светлая, тёмная и системная темы читаемы;
7. нет перенаправлений за пределы `base_url`.

Проверяйте именно те файлы проверочного каталога, чей отпечаток совпал.

## 6. Переключите за один шаг

Если хостинг поддерживает каталоги выпусков, переключите одну ссылку на новый
каталог. Если нет, используйте атомарную выкладку вашего хостинга. Не удаляйте
предыдущую успешную версию, пока не закончите проверку после переключения.

Сразу повторите короткую проверку через публичный адрес.

## 7. Откат

При 404, пропавшем ассете или поиске, неверном префиксе адреса или другой
поломке:

1. остановите дальнейшие изменения;
2. верните ссылку на предыдущий проверенный выпуск;
3. снова проверьте главную и вложенную страницы, ассеты и поиск;
4. запишите отпечаток неудачного выпуска и симптом;
5. исправьте исходники и пройдите заново: сборка → проверка → проверочный
   каталог.

Откат не пересобирает старую версию: он возвращает уже принятый неизменный
каталог.

## Что эта процедура не доказывает

Локальная сборка, проверка и проверочный каталог не заменяют требования
конкретного рабочего сайта к безопасности, доступности, лицензиям, доступам и
окнам изменений. Старый процесс на Node и Yarn тоже не доказывает готовность
переносимой выкладки.
