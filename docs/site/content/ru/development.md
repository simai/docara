# Разработка Docara

[Путь разработчика и AI-агента](/ru/development/developer-sdk/#путь-разработчика-и-ai-агента)
ведёт по шагам: найти возможность, составить план, посмотреть результат,
проверить изменение без записи (`dry-run`), применить его по хешу плана и
проверить. Все шаги используют одни и те же внутренние службы Docara.

Этот раздел предназначен для тех, кто развивает сам движок. Автору обычного
сайта не нужно менять тему: для сборки ему достаточно PHP, Composer и
Node.js 20+ из [быстрого старта](/ru/start/quick-start/).

## Как развивать возможности

Начинайте с самого простого уровня расширения: обычный Markdown, затем
типизированный компонент Docara, затем Smart-компонент из закреплённой версии
SIMAI Framework. Если исполняемого контракта ещё нет, добавьте запись о
потребности с явной безопасной заменой. Изменение не должно обходить схему,
описание компонента (manifest), точную ревизию, отрицательные тесты и
проверку в браузере.

Не начинайте со Smart-компонента только потому, что он есть во Framework.
Берите самый простой строительный блок, который решает задачу.

### 1. Проверьте обычный Markdown

Выберите обычный Markdown, если задачу решают заголовок, текст, ссылка,
список, цитата, блок кода, изображение или небольшая таблица.

Менять набор возможностей обычного Markdown можно только вместе с тестами
разбора и вывода, документацией и эталонным примером (fixture). Не разрешайте
сырой HTML как обход отсутствующей возможности.

### 2. Добавьте типизированный компонент Docara

Типизированный компонент подходит для повторяемого смыслового блока, который
PHP всегда выводит одинаково, например `card`, `steps`, `cta`, `features` или
`columns`.

1. Добавьте одно описание в `resources/component-catalog/typed/`.
2. Закрепите новый идентификатор рендерера с номером версии.
3. Опишите узкий синтаксис для автора и ограничения.
4. Добавьте эталонный пример и тесты рендерера: на правильный вызов и на
   отклонение неверного.
5. Добавьте одну Markdown-страницу компонента и проверьте её тем же
   PageBuilder.

Рендерер может использовать только проверенные утилиты и компоненты SIMAI
Framework: отдельной дизайн-системы он не создаёт.

### 3. Допустите Smart-компонент

Допуск Smart-компонента нужен, когда требуется точный компонент SIMAI
Framework и его поведение в браузере.

1. Получите от владельца компонента manifest с параметрами, состояниями и
   неизменяемой ревизией.
2. Закрепите в Framework lock ревизии поставщика и исходного репозитория,
   ассеты и их SHA-256.
3. Добавьте только сужающие метаданные Docara.
4. Проверьте параметры, ограничения, полноту зависимостей, темы, работу с
   клавиатуры, адаптивность и доступность.
5. Добавьте отдельную Markdown-страницу и эталонный пример. Публичный текст не
   переносите в manifest, настройки или `lang.json`.

Метаданные Docara не могут расширить manifest или сами повысить готовность
компонента. Подробные условия допуска описаны в разделе
[«Компонент SIMAI Framework»](/ru/development/smart-components/#компонент-simai-framework).

### 4. Зафиксируйте потребность

Если рендерер, manifest, ассеты или приёмка ещё не готовы, создайте
неисполняемую запись в `resources/component-catalog/requirements/`.

Она должна назвать:

- владельца;
- причину недоступности;
- безопасную замену;
- проверяемое условие допуска;
- честный статус `admission_pending`, `framework_gap` или `deferred`.

Такая запись делает недостающую возможность видимой, но не разрешает её
вызов.

### Как объявить возможность готовой

Запись о потребности нельзя переключить в `supported` на месте.

1. Удалите запись о потребности.
2. Добавьте исполняемую запись владельца: в набор обычного Markdown, в
   описания типизированных компонентов или в метаданные Smart-компонента с
   допуском по закреплённой версии.
3. Добавьте рендерер, тесты, документацию и эталонный пример.
4. Проверьте страницу в Markdown, машиночитаемый каталог, проверку сборки и
   браузеры.
5. Заявляйте статус только этой возможности.

Готовность одной записи не означает готовность Docara к выпуску или
готовность остальных компонентов.
