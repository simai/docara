# Smart-компоненты

Smart-компонент — переносимый элемент интерфейса. Его описание
(`manifest.json`), представления, шаблон и файлы стилей и скриптов
проверяются при сборке. Все компоненты проходят один путь:

```text
Markdown -> typed Document IR -> renderer registry
-> SmartComponentGateway -> DeclarativePageRenderer -> PageBuilder
```

Docara не выбирает способ вывода по имени компонента. Реестр поставщиков
находит владельца пространства имён, затем общий вход (`SmartComponentGateway`)
проверяет описание, представление, пресет, параметры, шаблон и файлы.
Неизвестное или небезопасное значение останавливает сборку.

## Кому принадлежат компоненты

| Пространство имён | Поставщик | Назначение |
| --- | --- | --- |
| `ui.*` | закреплённая версия SIMAI Framework (`simai-framework.lock.json`) | Smart-компоненты SIMAI Framework |
| `docara.*` | пакет Docara (`docara.package`) | оболочка и навигация Docara |
| пространство имён проекта | `project.<пространство>` | компоненты конкретного сайта |

`ui.alert`, `ui.button`, `docara.brand`, `docara.navigation`, `docara.toc` и
`docara.preferences` проходят через тот же общий вход. Старые имена
`docara.header` и `docara.outline` записаны в описании компонента как
псевдонимы, а не в коде.

## Компонент проекта

Объявите одно пространство имён в `docara.json`:

```json
{"smart":{"namespace":"project"}}
```

Компоненты лежат только в папке `smart/`. Настройки и Markdown не могут
указать класс PHP, функцию или путь к шаблону.

```text
smart/project.notice/
├── manifest.json
├── view/default.json
├── template/default.php
└── assets/notice.css
```

`manifest.json` записывается в формате Smart-компонентов SIMAI Framework.
Готовые примеры, в том числе `project.notice`, есть в заготовке
`docara init --template=showcase --lang=ru`; в обычной заготовке папки
`smart/` нет. Пошаговое создание своего компонента — в уроке
[«Первый компонент проекта»](/ru/start/first-component/). В Markdown
компонент вызывается так:

```markdown
:::project.notice
{"title":"Компонент проекта","text":"Собран общим конвейером."}
:::
```

Новый компонент `project.*` не требует правок в коде Docara. Сборка
остановится, если имя повторяется, пространство имён чужое, в папке есть
символическая ссылка, путь выходит за папку через `..`, или представление,
пресет, параметр, шаблон либо файл неизвестны.

### Примеры в заготовке

После `docara init --template=showcase` страница `/ru/project-demos/`
показывает два компонента проекта:

- `project.install-builder` собирает и копирует команду Composer из полей
  `ui.input` и `ui.checkbox`;
- `project.product-configurator` считает демонстрационную цену в браузере;
  варианты выпадающего списка `ui.dropdown` в его слоте `options` — дочерние
  `ui.list-item` с `type=text`.

Оба примера не обращаются к серверу, ничего не заказывают, не принимают
оплату и не выполняют команд. Их можно вызывать и через подчёркивание —
`project.install_builder`, `project.product_configurator`, — но основные имена
пишутся через дефис. Все четыре компонента Framework проходят тот же реестр и
общий вход, что и остальные; их описание, шаблон, файлы и поведение в
браузере сверяются с закреплённой версией до вывода HTML.

`ui.list-item` поддерживается здесь узко: только как текстовый вариант в
`ui.dropdown`. Значки, аватары, метки и самостоятельный `ui.list-item` не
поддерживаются. Нельзя заменять варианты массивом `items`, своей разметкой или
копией компонента Framework.

### Какое представление выбирается

Одинаково для любого поставщика: явно указанное представление (`view`)
важнее всего; если его нет, представление выбирает пресет (`preset`); если
нет ни того, ни другого — `default`. Это данные компонента, поэтому новый
компонент или вариант не требует условий в коде Docara.

## Шаблон и файлы компонента

Шаблон — обычный PHP-файл. Docara передаёт ему переменные в формате
Smart-компонентов SIMAI Framework 5 и не вводит своего языка шаблонов.

| Переменная | Что содержит |
| --- | --- |
| `$id` | идентификатор узла (строка) |
| `$smart` | полное имя компонента |
| `$manifest` | проверенное описание компонента (массив) |
| `$view` | выбранное представление (массив) |
| `$preset` | выбранный пресет или пустой массив |
| `$props` | проверенные параметры из вызова (массив) |
| `$childrenHtml` | готовый HTML дочерних компонентов (строка) |
| `$slot` | имя слота или пустая строка |

Выводите параметры только через экранирование, например
`<?= htmlspecialchars((string) ($props['title'] ?? ''), ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8') ?>`.
Объект `$view` и `SmartTemplateContext` относятся только к старым шаблонам
внутри пакета Docara; новые шаблоны их не используют.

Шаблон проекта считается доверенным кодом разработчика. Путь к нему
определяется только папкой компонента и записями в `manifest.json` и
представлении. Стили и скрипты тоже перечисляются в `manifest.json`,
сверяются с файлами и подключаются к страницам вместе с остальными файлами
сборки.

Подписи интерфейса сайта берутся из `content/<язык>/lang.json`, текст
страниц — из Markdown. Описание компонента и настройки проекта не
источник текста документации.

### Формат компонента

Формат компонента называется `sf.smart_artifact_abi`, версия `1.0.0`,
идентификатор совместимости `sf-smart-artifact-abi-v1`. Им владеет SIMAI
Framework. Старое имя `sf5.smart.artifact.v1` обозначает только прежнее
расположение файлов, а не второй формат. Закреплённая ревизия
`b3cdff87563ff78e7eddf044048a4b298fc69036` передаёт представление, пресет,
слот и правила оживления одинаково в SIMAI Framework 5 и в Docara.

`docara schema smart --json` возвращает схему `smart.manifest.schema.json`
SIMAI Framework без изменений; `manifest.json` из заготовки проходит её
напрямую. Дополнительные требования Docara проверяет отдельный набор правил
`docara.smart_admission.v1`, а не другая схема. `inspect smart ... --json`
одинаково показывает формат для `ui.*`, `docara.*` и компонентов проекта; как
поставщик подключил компонент, видно в полях `provider_adapter` и
`template_abi`.

## Проверка

```bash
docara doctor
docara inspect smart project.notice --json
docara validate smart project.notice
docara build production
docara verify-static build_production
```

Новый компонент начинайте с плана: `docara scaffold smart project.name
--dry-run`, затем `docara scaffold --apply=<plan_id>`. Подробно — на
странице [«SDK для разработчика и AI-агента»](/ru/development/developer-sdk/).

Полная сборка и сборка одной страницы (`--page`) используют один и тот же
построитель. Если изменились адреса страниц, нужна полная сборка; текст
существующей страницы можно пересобрать отдельно.

## Новый компонент SIMAI Framework

Этот раздел — для тех, кто развивает саму Docara. Новый вызов `:::ui.*` не
появится от правки разбора Markdown, схемы или каталога: допуск определяет
только точный файл закрепления `simai-framework.lock.json`.

Сначала убедитесь, что задачу не решают обычный Markdown или готовый блок
Docara, — см. [обзор раздела](/ru/development/#как-развивать-возможности).
Затем:

1. добавьте описание компонента по публичной схеме
   `sf.smart_artifact_abi` / `smart.manifest.schema.json`: параметры, способ
   вывода и неизменяемую ревизию источника;
2. добавьте описание в файл закрепления SIMAI Framework с ревизией
   поставщика и SHA-256;
3. перечислите все файлы, которые нужны компоненту, включая зависимости
   зависимостей;
4. добавьте узкие сведения об использовании в Docara в
   `resources/component-catalog/smart/`: они не могут расширять описание
   компонента;
5. добавьте тесты на правильные и неправильные параметры, ограничения,
   зависимости и закрепление;
6. проверьте в браузере поведение, клавиатуру, темы, ширину экрана и
   доступность;
7. добавьте одну страницу документации в Markdown и отдельный тестовый
   пример; ни описание компонента, ни `lang.json` текстом страницы не владеют.

Каждый обязательный файл из описания должен попасть в план подключения или
быть исключён правилами Docara с конкретной причиной. `verify-static` сверяет
каждый опубликованный файл Framework с закреплением: путь, тип, SHA-256 и
полный набор. До очистки папки сборки проверяется содержимое каждого
закреплённого файла и то, что набор файлов совпадает со всеми зависимостями
допущенных компонентов.

Ядро и утилиты Framework публикуются отдельно, с путями как в исходной папке
`distr`: так ядро находит свои части без запросов в сеть. Файл в этой папке
ещё не означает, что компонент допущен: для этого нужны принятое описание и
правила Docara. Обработчики на сервере, привязка данных и выполнение действий
из коммерческих пакетов SIMAI в Docara не допускаются; это ограничение видно в
машинном каталоге.

### Как читать каталог компонентов

Поле `authoring.parameters` описывает то, что пишет автор, а не итоговые
параметры шаблона. `required: false` значит только, что параметр можно не
указывать. `default` есть, когда точное значение задано в
`atlas.example_props`; иначе параметр отсутствует, пока его не укажут явно
или не применят пресет. `preset` — отдельный необязательный параметр.
`validation` переносит правила для строк и чисел, а `mirrors` показывает, какое
связанное свойство заполняется автоматически, например доступное имя.
`authoring.constraints` без потерь переносит `allowed_combinations` и
`requires` из описания, чтобы разработчик и AI-агент не собирали
несовместимые сочетания.

Сборка требует, чтобы сведения в каталоге точно совпадали с описаниями,
допущенными закреплением: лишний файл сведений, отсутствующее описание,
несовпадающий хеш или подвижная ревизия останавливают сборку. Схема
`docara.component_call.v1` проверяет только форму вызова `ui.*` и не решает,
допущен ли компонент.

Сведения Docara не могут повысить готовность компонента или расширить его
название, категорию и состояния. Поддерживаемый компонент должен быть
помечен `safe_to_suggest` и `safe_to_render`. Его состояния совпадают с
состояниями описания в том же порядке, кроме перечисленных в
`consumer_policy.excluded_states`; каждое исключение связано с конкретной
запрещённой парой «свойство — значение», которая сама проверяется по схеме.
Описание поведения берётся из правил Docara, а не копируется из более
широкого описания Framework.

Точные поддерживаемые вызовы, параметры и примеры — в
[справочнике компонентов](/components/).

### Как зафиксировать ещё не готовую потребность

Если способ вывода или набор для допуска ещё не готов, добавьте
неисполняемую запись в `resources/component-catalog/requirements/` с
состоянием `admission_pending`, `framework_gap` или `deferred`. В записи нужны
владелец, причина, чем пользоваться пока и условие допуска. Запись делает
нехватку видимой, но не включает вызов.

Такая запись никогда не превращается в `supported` на месте. Когда всё
готово, её удаляют, а возможность появляется из своего источника: профиля
Markdown, описания блока Docara или сведений о Smart-компоненте с точным
допуском в закреплении. Для работающей возможности обязательны способ вывода,
тесты, документация и тестовый пример. Файл `_docara/component-catalog.json`
в сборке — не основной реестр SIMAI Framework и не подтверждает готовность к
выпуску. Старая схема описания v1 встречается только во внутренних файлах
пакета для совместимости и не является ни публичной схемой, ни вторым
форматом.
