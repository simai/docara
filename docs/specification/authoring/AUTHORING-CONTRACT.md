# Контракт авторинга Docara

Статус: целевой обязательный контракт

Этот документ отвечает на один вопрос: где автор, переводчик и разработчик
должны менять данные, чтобы результат был предсказуемым. Архитектурные причины
описаны в [DOCARA-TZ.md](../DOCARA-TZ.md).

## 1. Главное правило

Одна публичная страница одной локали имеет один физический Markdown-файл:

```text
content/<locale>/<route>.md
```

Текст страницы нельзя хранить или дублировать в PHP, language pack, component
manifest, component catalog, JSON-конфигурации или generated-файле.

## 2. Структура контента

```text
content/
├── ru/
│   ├── lang.json
│   ├── index.md
│   ├── section.json
│   └── components/
│       ├── index.md
│       ├── section.json
│       ├── badge.md
│       └── alert.md
└── en/
    └── ...
```

Маршруты выводятся механически:

- `content/ru/index.md` -> `/ru/`;
- `content/ru/components.md` -> `/ru/components/` (рекомендуемая форма);
- `content/ru/components/index.md` -> тот же route только как совместимая
  альтернативная форма;
- `content/ru/components/badge.md` -> `/ru/components/badge/`.

Не должно существовать скрытого projector, который создаёт публичный route без
Markdown-файла.
Одновременные `components.md` и `components/index.md` fail-closed как
`PAGE_SOURCE_ROUTE_AMBIGUOUS`.

## 3. Что хранится в Markdown

Markdown владеет всем page-owned контентом:

- заголовками, абзацами, списками, таблицами и цитатами;
- примерами и исходным кодом;
- вызовами inline и block Smart-компонентов;
- описаниями параметров компонента;
- предупреждениями, ограничениями и ссылками;
- короткими метаданными материала в front matter.

Минимальный пример:

```markdown
---
title: Бейдж
description: Короткая метка для статуса или версии.
tags: [ui, status]
draft: false
---

# Бейдж

Используйте бейдж для короткой метки рядом с текстом.

:badge[Новое]{type=tonal scheme=primary size=1}
```

Git revision, автор последнего изменения и дата изменения вычисляются только из
истории Git exact source, если она доступна. В Composer dist без `.git` эти поля
равны `null`: filesystem `mtime` отражает время распаковки и никогда не является
публичной metadata страницы. Версия Framework берётся из immutable lock. Эти
значения не следует вручную копировать во все страницы.

## 4. Что хранится в конфигурации

Конфигурация выбирает композицию, но не содержит текст статьи:

```text
engine defaults
  -> docara.json
  -> section.json от корня локали к странице
  -> <page>.page.json
```

- `docara.json` — локали, route policy, Framework lock, layout, глобальные
  области и возможности сайта;
- `section.json` — настройки каталога и его потомков;
- `<page>.page.json` — только исключения конкретной страницы.

Если исключений нет, `.page.json` не создаётся. В config запрещены HTML,
Markdown-проза и CSS-фрагменты.

## 5. Общие переводы локали и внутренние сообщения

Единственный источник повторяющихся видимых интерфейсных строк локали —
`content/<locale>/lang.json`. В нём находятся поиск, содержание, копирование,
переходы, accessibility labels и другие общие подписи. Статьи и документация
компонентов остаются в Markdown.

Файл имеет schema ID `docara.lang.v1` и version `1`. Корневые namespaces
ограничены общими UI-контурами (`search`, `navigation`, `reader`, `shell`,
`language`, `redirect`, `accessibility`, `copy`, `toc`, `transitions`,
`common`); `pages`, `components`, `catalog` и `examples` запрещены. Значения —
короткий plain text без Markdown, HTML и CSS. Исходный `lang.json` не
публикуется как статический asset.

Публичного `resources/i18n` в целевой архитектуре нет. `site.json` также не
поддерживается: бренд, меню, CTA, layout и поведение задаются
`docara.json`, `section.json` и `.page.json` как структурированная композиция.
Обратная совместимость с `site.json` не требуется.

Сообщения CLI и сборщика принадлежат пакету. Их возможная локализация хранится
отдельно, не доступна как контент страницы и не участвует в публичной сборке.

## 6. Синтаксис Smart-компонентов

Inline-компонент используется внутри текстового потока:

```markdown
:badge[Новое]{type=tonal scheme=primary size=1}
```

Block-компонент создаёт самостоятельный смысловой блок:

```markdown
:::alert{type=info}
Настройка применяется после новой сборки.
:::
```

Короткое имя разрешается registry в полное имя. Все вызовы компилируются в один
тип IR-узла `component` и проходят один Smart Component Gateway.

Автор не пишет внутренние классы Framework и не передаёт готовый HTML в обход
gateway. Произвольный HTML допускается только через явно разрешённый,
санитизированный продуктовый компонент с отдельной security policy.

### Контентная поверхность

`:::surface` — зарегистрированный контейнер для ограниченной или full-bleed
полосы внутри границы активного Layout Region. Внешняя ширина выбирается только
`content|full`, внутренняя — `container|full`; фон допускает только существующий
локальный `/assets/...` файл, а fit, position, overlay, strength, padding и tone
задаются закрытыми enum/token значениями. Произвольные CSS/class/style/path и
remote/data URL не являются частью контракта.

Допустимые children определяются capability и container contract в реестре,
а не длиной fence. В v1 вложенные Surface и semantic landing-блоки Hero,
Showcase и Promo запрещены. Декоративный background всегда получает пустой
`alt` и `aria-hidden`; смысловое изображение остаётся обычным Markdown media.

## 7. Страница документации компонента

Страница компонента является обычным Markdown-файлом. Рекомендуемый порядок:

1. название;
2. одно короткое объяснение назначения;
3. общий интерактивный пример без отдельного заголовка «Пример»;
4. по одному разделу на пользовательский параметр;
5. в разделе параметра — понятное название, короткое объяснение с именем
   параметра, таблица допустимых значений и компактные пример/код;
6. только реальные ограничения, если они влияют на использование.

Не выводятся служебные разделы без пользовательской ценности: внутренний
source path, readiness bookkeeping, пустые «Состояния», «О компоненте» или
«Что учесть».

Manifest компонента хранит только машинный контракт. Редакторский текст и
примеры находятся в Markdown.

## 8. Медиа и assets

- page-owned изображения живут рядом с контентом или в документированной
  папке assets сайта;
- component-owned icons/scripts/styles принадлежат manifest компонента;
- Framework assets поступают только из immutable Framework lock;
- generated HTML не содержит ссылок на случайные файлы из source checkout;
- изображение имеет alt; декоративное изображение помечается явно;
- соотношение сторон задаётся поддерживаемым параметром, без растяжения.

## 9. Что автор не редактирует

Следующие данные производны и могут быть полностью пересозданы:

```text
var/cache/ir/**/*
var/cache/site-index.json
var/cache/search-index.jsonl
build/**/*.html
```

Обязательной сериализации IR нет: `MarkdownCompiler` создаёт typed IR в памяти.
JSON/JSONL допустимы только как удаляемый cache, поисковый индекс,
диагностический `--dump-ir` или test evidence. Ручное изменение IR, индекса
или HTML является ошибкой процесса.

`build/.docara/design-atlas.json` и `build/.docara/schema-reference.json` также
производны. Автор вставляет в Markdown только допущенные декларативные узлы
`atlas_index` и `schema_reference`; карточки и поля поступают из admitted
registries/schemas. Эти receipts нельзя использовать как параллельный источник
поясняющей прозы или редактировать вручную.

## 10. Диагностика

Ошибка синтаксиса, неизвестный компонент или неверный prop должны сообщать:

- локаль и route;
- исходный Markdown-файл;
- строку и колонку;
- имя узла или компонента;
- переданное и ожидаемое значение;
- короткий способ исправления.

Сообщение не должно требовать от автора знания внутренних PHP-классов.

## 11. Быстрый цикл правки

После одной полной сборки редактор может пересобрать одну страницу:

```bash
php vendor/bin/docara build production --page=/ru/components/badge/
```

Single-page build обязан использовать тот же `PageBuilder` и весь тот же
конвейер, что и полный build; различается только выбранный набор route. После
изменения навигации, глобального config, Framework lock или
структуры сайта выполняется полная сборка.

## 12. Проверочное правило

Если для новой страницы приходится добавлять редакторский текст в PHP,
language pack, catalog record или отдельный projector, реализация нарушает
контракт. Правильная развилка:

```text
новый материал -> content/<locale>/<route>.md
общая подпись локали -> content/<locale>/lang.json
новая композиция -> JSON config
повторно используемое поведение -> Smart-компонент
всё остальное -> производный результат движка
```
