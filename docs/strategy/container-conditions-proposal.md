# Контейнерные условия: принятое решение и реализация кандидата

Статус: решение принято владельцем; классы и конечный JSON-профиль добавлены в изолированный source-кандидат. Опубликованная поставка ещё не подтверждена. Основание — [план](foundation-plan.md) и [пакет принятия](foundation-decision-packet.md); прежний [эксперимент](foundation-container-proof.json) не заменяет приёмку новой сборки.

## Рекомендуемая граница

Viewport-условия `sm:`, `md:` и остальные сохраняют прежний смысл. Контейнерные условия получают отдельный префикс `cq-`, чтобы одинаковое имя контрольной точки не скрывало разные источники размера.

Предлагаемый синтаксис:

```html
<div class="query-container">
  <div class="flex flex-col cq-sm:flex-row">...</div>
</div>
```

`query-container` обозначает inline-size query container. `cq-sm:` действует от порога sm ближайшего подходящего родителя; само объявление контейнера не задаёт ширину, отступы или внешнее оформление. Пороги компилируются из конечного набора SF5, не из произвольного значения пользователя. В доказательстве sm равен520px; переиспользование шкалы не означает, что viewport и контейнер — одно условие.

Для именованных контейнеров принята форма `query-container/sidebar` и `cq-sm/sidebar:flex-row`. Имена допускаются только из явного build-time registry; вложенный контейнер с другим именем не перехватывает запрос к sidebar. Первый профиль объявляет sidebar, четыре порога sm/md/lg/xl и конечные роли display/flex/grid/gap/justify/align. Один query-layout модуль сохраняет стабильный порядок порогов и приоритет осей gap независимо от времени загрузки сети.

Не добавлять общий `container` как псевдоним query-container: этот класс уже имеет другую задачу. Не менять существующие breakpoints. Не требовать JS ResizeObserver для базовой геометрии. При отсутствии container-query поддержки сохранять пригодное базовое состояние, а не подменять условие viewport-запросом.

## Ограничение размера и дальнейшая эволюция

Генерация остаётся предварительной, модульной и конечной. Первый профиль включает только требуемые сценарием группы компоновки: display, flex direction/wrap, gap, grid columns и выравнивание. Пакет не генерирует автоматически произведение всех utilities × states × viewport × containers × names.

Точные группы, значения, имена и сочетания должны входить в машиночитаемый манифест профиля. Новые сочетания добавляются отдельным изменением этого профиля с тестами и замером. Произвольные runtime-значения и компиляция CSS на сервере потребителя не вводятся.

До выпуска измерить фактическое число селекторов, raw/gzip размер и число запросов каждой группы; численного результата сейчас нет. Loader должен строить точные границы из CSS нового профиля, включая escaped `/` и `:`, и отвергать неподдерживаемые имена/сочетания. Именованный nested сценарий, минимальная/максимальная граница и изолированная загрузка обязательны.

## Реализация и приёмка

В source-кандидате профиль хранится в src/core/contracts/container-conditions.v1.json. Штатный generate-container-conditions.mjs создаёт Sass-конфигурацию и точные правила Loader, --check проверяет свежесть. Новые rule.js импортированы в исполняемый Core и проверяются общим тестом utility-rule-imports. До выпуска обязательны реальные CSS↔Loader, nested/boundary/browser проверки, размер продукта и документация, соответствующая установленной версии.
