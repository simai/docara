# Docara: один источник знаний для человека и ИИ

Статус: **предлагаемый контракт для согласования и реализации**, не описание уже выпущенного API. Дата: 8 сентября 2026 года.

После уточнения владельца этот документ рассматривается как **продуктовый Knowledge-пилот [AI First](ai-first-concept.md)**. Не создавать два конкурирующих публичных manifest-формата: предложенные ниже пути и поля необходимо согласовать с выбранным минимальным профилем. Существующий authoring SDK Docara не заменяется. Общий стандарт не ограничивается документацией и не требует MCP для статической публикации.

## Пользовательский результат

Автор ведёт обычную документацию. При сборке Docara выпускает человеческий сайт и согласованное представление для ИИ. Пользователь передаёт агенту адрес документации, и агент может найти нужную страницу, прочитать инструкцию или код, установить версию и сослаться на источник без доступа к репозиторию.

Для MCP-клиента предоставляется отдельный read-only адаптер этой же публикации. Автор не поддерживает второй комплект статей, не запускает LLM при сборке и не оплачивает обязательный векторный сервис.

## Что уже есть

В Docara есть Developer/AI SDK, локальный stdio MCP, manifests/catalogues, validation, QA и documentation tracking. Их сохраняем. Локальный authoring MCP работает с проектом и может иметь отдельно разрешённые операции записи. Новый reading-сценарий таких полномочий не имеет.

UI Studio остаётся владельцем Smart-контрактов. Docara связывает объяснения с ними, но не копирует их в собственный вручную редактируемый реестр.

## Три способа доступа

| Способ | Что нужно пользователю | Что требуется хостингу |
| --- | --- | --- |
| Читать HTML по URL | Агент с web/fetch-доступом | Обычный статический сайт |
| Читать knowledge files по URL | Агент, умеющий загружать текст/JSON | Тот же статический сайт |
| Подключить MCP | MCP-клиент и адрес сервиса либо локальный bridge с URL сайта | Для remote MCP — отдельный процесс; для local bridge сайт остаётся статическим |

Обычная ссылка на сайт не является MCP endpoint. `llms.txt` помогает обнаружить знания, но не гарантирует, что любой AI-клиент автоматически загрузит их. Для приватной документации доступ ограничивается инфраструктурой и в HTML, и в knowledge-представлении.

## Предлагаемая минимальная поставка

### Статическая проекция

Имена ниже предлагаются как публичный контракт, но до принятия не должны появляться в справочнике как работающие команды или URL:

```text
llms.txt
_docara/knowledge/index.json
_docara/knowledge/pages/<stable-id>.md
```

`llms.txt` — короткое представление сайта и ссылки на языковые/тематические разделы и индекс. Не помещать туда целиком весь каталог из сотен страниц.

Индекс содержит schema/version, documentation version, knowledge digest и для каждой страницы: stable ID, title, locale, canonical URL, content URL, content hash и при наличии public contract refs. В нём нет host paths, credentials, авторских комментариев, внутренних workflow и полной resolved-config provenance.

Страница содержит читаемое содержание, заголовки, ссылки, списки, таблицы и точный исходный код примеров. Ссылки разрешаются относительно опубликованного URL с поддержкой site base path и locale prefix. Никаких LLM-сводок, меняющих смысл исходника.

### Источник генерации

Предпочтительно использовать существующий Document IR и разрешённые component descriptions/примерные source tabs, а не очищать готовый HTML регулярными выражениями. Так сохраняются код, семантика таблиц и содержимое компонентов.

До принятия реализации проверить покрытие IR: обычный Markdown, typed/container components, shared examples и сгенерированные reference pages. Если для конкретного узла нет смыслового текстового представления, выводить диагностируемую ограниченную проекцию со ссылкой на HTML, а не придумывать описание.

Навигация, футер и UI панели не дублируются в каждом документе. Скрытая вкладка кода не должна исчезнуть только из-за HTML-атрибута `hidden`.

### Включение

Предлагается явная настройка knowledge export на уровне сайта. Для новых публичных шаблонов документации — включено. Для существующих проектов — осознанное включение при обновлении с предварительным списком экспортируемых страниц.

Это сохраняет принцип автоматической подготовки **после включения** и не расширяет неожиданно поверхность распространения старой документации. Черновики исключаются. Скрытие из меню не считается приватностью. Исключения из knowledge export не являются средством контроля доступа.

## Read-only MCP

Минимальный набор: список/поиск документов и чтение одного документа по стабильному ID; resources для индекса и страниц. Точный naming согласовать с существующим SDK перед реализацией, не объявлять его задним числом текущим API.

Первая версия bridge запускается с одним явно настроенным site URL. Аргументы tool call не позволяют переключить origin, читать локальный файл или получить произвольный URL. Источник выбирает оператор, не текст найденной статьи.

Для HTTP deployment: официальный MCP lifecycle и версия протокола; JSON-RPC; корректные POST/GET/notifications; проверка Origin; ограничения размера и времени; HTTPS; отдельный механизм аутентификации для непубличного сайта. Локальные `.test` адреса доступны только там, где настроены DNS/TLS/сеть.

Возвращаемый результат включает ссылку, язык, версию и content hash. Read-only означает отсутствие scaffold/apply/exec и отсутствие полномочий авторского SDK.

## Жизненный цикл

1. Полная сборка вычисляет IR и набор публичных страниц.
2. Экспорт строится в том же временном каталоге, что HTML.
3. Верификатор проверяет ссылки, hashes, coverage и отсутствие запрещённых полей.
4. Успешная сборка атомарно публикует согласованную пару HTML/knowledge.
5. Одностраничная пересборка обновляет соответствующий knowledge-документ и digest индекса. Изменение topology требует полной сборки по существующим правилам.
6. Удаление страницы удаляет её запись и документ; кеш клиента различает версии и проверяет digest.
7. Ошибка обязательной проекции блокирует продвижение кандидата, сохраняя предыдущую сборку. Не оставлять свежий HTML со старым knowledge index.

## Защищаемые границы

- Документация — недоверенные данные для агента, не разрешение выполнять команды.
- Нет обхода прав через AI endpoint и нет раздачи внутренних источников по догаданному пути.
- Запрещены traversal, выход за origin через redirects, чтение file URLs и утечка служебных путей.
- Для сетевого bridge нужны контролируемые redirects, timeout/size limits и явный режим доверия к локальному origin. Не отключать TLS-проверку в пользовательском примере.
- Хеш проверяет целостность в рамках доверенной публикации; он не заменяет аутентификацию издателя.
- Нет обязательной зависимости от конкретной модели, облачного провайдера или эмбеддингов.

## Приёмка

| Сценарий | Ожидаемое доказательство |
| --- | --- |
| Markdown, таблица, пример кода | Смысл и точные байты code fence сохранены |
| Два языка и site под `/docs/` | Правильные URL, locale, относительные ссылки |
| Draft/внутренний комментарий | Не присутствуют в knowledge-экспорте |
| Shared example и скрытая вкладка HTML | Код доступен, iframe markup не подменяет пример |
| Изменение одной страницы | Меняются нужный content hash и digest; остальные документы неизменны |
| Удаление страницы | Нет записи и старого файла после полной сборки |
| Ошибка генерации | Предыдущая сборка остаётся согласованной |
| Два одинаковых входа | Побайтово одинаковая knowledge-поставка |
| Поиск и чтение через MCP | Независимый клиент получает текст, source URL и version |
| Вредоносный ID/URL/redirect | Нет доступа вне разрешённой публикации |
| Несовместимая версия индекса | Явная диагностика, а не неверный разбор |
| Отключённый export | Сайт работает как раньше, documentation не обещает отсутствующие файлы |

## Изменяемые владельцы

- Docara: export compiler, схема настройки, verification, read-only adapter, документация и тесты.
- ui-doc: включение принятого контракта, страница AI-подключения, точный engine lock.
- UI Studio: существующие ресурсы контрактов; изменения только при доказанном несовпадении.
- ui-control: связь поставок и evidence; не реализация адаптера.
- Larena: этот этап не добавляет AI-пакеты и не меняет принятую архитектуру.

## Порядок внедрения

Сначала принять владельца knowledge contract, IR-проекцию и режим включения; затем exporter с тестами; затем bridge; затем два документационных потребителя; затем совместимая версия Docara и публикация. Сначала полнота и точность базового извлечения, после — семантический поиск при измеренной необходимости.

## Почему здесь пока проект, а не готовая функция

Введение публичной knowledge-схемы и нового MCP reading-интерфейса меняет архитектурный контракт Docara. Общий запрос на улучшение достаточен для анализа и подготовки проекта, но действующие правила разработки требуют принятия точной архитектуры перед значимым новым runtime-контрактом. Этот документ фиксирует решение для такого принятия; не скрывает незавершённое внедрение под видом готового endpoint.
