# Подготовка согласованной поставки фундамента

Это исполняемая подготовка к разделу выпуска [генерального плана](foundation-plan.md), не новый план, не разрешение на публикацию и не приёмка.

## Текущее основание

- [Снимок 44 исходных файлов](foundation-source-snapshot.json) фиксирует working bytes в изолированном ui-loader. Чужой тест admin-menu и node_modules исключены. Это ещё не release source revision.
- Полный unit suite с чистым ui-doc@1dc8e0537fc3d4cde3b68b3bbf92a51f5ab9b567: 192/195 PASS; три отказа — source artifact drift таблицы. Проверка content-spacing документации отдельно прошла.
- Выбранные поведенческие сценарии таблицы/диалога прошли три движка. WebKit не заменяет Safari. Полный каталог и все условия плана этим не закрыты.
- [Публичный пакет](foundation-decision-packet.md) пока предложение. Автоматическое продолжение цели не является его принятием.

## Последовательность без подмены происхождения

1. Завершить и принять публичные решения, реализовать выбранные семейства, затем обновить snapshot и полный перечень затронутых контрактов. Не фиксировать текущий локальный кандидат как окончательный фундамент до этого.
2. Подготовить точный набор source-изменений отдельно от чужой работы. Проверить diff, символические ссылки, метаданные, тесты и разрешённые границы Git/release. Никакого `git add .` по смешанному worktree.
3. Зафиксировать исходный код точной ревизией. Первая source-ревизия может содержать ещё прежние derived metadata; это явно не прошедший release gate. Не выдавать её за готовый выпуск.
4. Из чистых checkout этой source-ревизии и точной builder-ревизии построить продукты дважды, сравнить весь output и diagnostics. Проверить generated-only состав ui/ui-smart, идентичность входов и независимого потребителя.
5. После соответствующих gates зафиксировать generated runtime ревизии; затем штатно вычислить metadata от точных source/runtime/ui refs. Производная metadata-ревизия ссылается на зафиксированный код, а не на сама-себя. Повторно проверить, что изменение только metadata не меняет runtime bytes.
6. Перезапустить полный source/registry/Studio контракт и документационные проверки. Если gate всё ещё не проходит, выпуск запрещён независимо от локальных браузерных PASS.
7. Только после release acceptance обновлять точные consumer locks, собирать ui-doc/Docara, проводить static/browser checks, inventory текущей публикации, backup вне web-root, проверяемый rollback и post-publication resource/style readback.

## Ограничения текущего refresh-инструмента

`scripts/refresh-smart-studio-provenance.mjs` проверен по исходнику: берёт source root из cwd, ui-smart и ui — из соседних каталогов; refs задаются явно через `--source-revision`, `--runtime-revision`, `--ui-revision`. Без `--write` только показывает список будущих изменений. Он обходит весь Smart-каталог, не один table manifest; нельзя запускать его в смешанном main checkout для точечной правки.

Инструмент пересчитывает только уже перечисленные `source_artifacts`. Новый `src/smart/table/js/smart-element.js` поэтому требует проверки полноты artifact inventory до обновления хешей. Не считать совпадение существующих хешей доказательством полного охвата новых исходников. Не добавлять фиктивные hashes текущих bytes к старой source-ревизии.

Точный release layout и финальные команды будут определены после выбора refs и прохождения gates. Имена временных product-каталогов не являются версиями, lock-файлами или опубликованными адресами.
