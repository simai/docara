# Где хранить стратегию и как двигаться дальше

Дата: 8 сентября 2026 года. Статус: рабочий порядок для подготовленного пакета; перенос владельцев, создание репозитория стандарта и новые runtime-контракты не выполнены.

## Решение на сейчас

Сохранять **один текст каждого документа** в `docara/docs/strategy/`, а `ui-control` использовать как точку обнаружения межпродуктовой работы. Уже существующий указатель `ui-control/control/STRATEGY-2026-09-08.md` ведёт на пакет. README пакета — его актуальный вход; dated baseline — историческое свидетельство, а не текущий статус всех репозиториев.

Это промежуточное размещение результатов, не объявление Docara владельцем всей архитектуры SIMAI. Оно позволяет продолжать работу уже сейчас без дублирования и без рискованного переноса canonical контрактов.

Не рекомендую сейчас переносить всё в ui-control: это удобно для навигации, но создаёт ложное впечатление владения backend и открытым стандартом. Не рекомендую и отдельный новый репозиторий только ради нескольких ещё обсуждаемых файлов. Сначала стабилизировать документы; затем одним согласованным переносом сохранить lineage и оставить redirect-указатели.

## Как отличать актуальное от исторического

- **Видение владельца:** цель, аудитория, разделение данных/структуры/поведения/представления. Это основание для проектирования.
- **Рабочая редакция:** изложение этого видения и предлагаемые решения. Текущий пакет относится к этой категории, пока не принят конкретный текст.
- **Принятый контракт продукта:** точная схема/API в репозитории владельца. При конфликте не переписывается общей roadmap автоматически.
- **Baseline:** дата, ref и граница проверки. Он не обновляется задним числом, чтобы выдать старый PASS за новую приёмку.
- **Реализовано / проверено / опубликовано:** отдельные статусы с собственной ссылкой на evidence и ревизию.

У каждой следующей задачи должны быть исходный документ, владелец, ограниченный результат, зависимости и проверка. Принятые переносимые решения регистрируются в Project Technology (`graph/specs`) через штатный owner-approved механизм. До принятия данный пакет — вход для такой регистрации, а не ручная подмена canonical graph. Локальный workflow хранит журнал выполнения, но не становится единственным источником архитектуры.

## Что можно и нельзя делать из текущего состояния

Можно использовать ДНК как контекст для обсуждения и подготовки архитектуры, ссылаться на найденные продуктовые контракты, уточнять словарь и составлять fixtures будущего стандарта. При описании готовых продуктов ссылаться только на проверенные существующие возможности.

Нельзя из статуса «концепт» выводить разрешение менять принятые схемы, выдавать экспериментальные URL за доступные, объявлять новый открытый стандарт опубликованным или обновлять release-lock без приёмки. Регистрация canonical технологии, новый репозиторий, лицензия и публикация — отдельные решения.

## Передача новому треду

Дать сначала [ДНК](platform-dna.md), затем этот файл и только относящийся к задаче продуктовый контракт. Для AI-интеграций дополнительно дать [AI First](ai-first-concept.md) и [Docara Knowledge](docara-ai-knowledge-proposal.md). Не требовать чтения всей истории чата.

Новый тред проверяет актуальные исходники и изменения рабочего дерева; не считает сентябрьский baseline вечным. Если он меняет направление, оставляет понятное решение с причиной и ссылкой, а не отдельную противоречащую копию ДНК.

## Сохранность

Файлы записаны локально и доступны после завершения чата. На данном этапе они **не закоммичены и не отправлены в remote**; локальное сохранение не является резервной копией на другом устройстве. Не удалять рабочий checkout до отдельной фиксации. Для устойчивой межмашинной ссылки нужен согласованный Git-коммит только относящихся к задаче файлов, затем разрешённая публикация.

Существующие незавершённые изменения компонентов, runtime Docara, compatibility ledger и Федерации не входят в эту документную работу. Никакой общий `git add .` для её фиксации не допускается.
