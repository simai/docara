# Smart и внешний шаблон: проверенная граница

## Удаление владельца с открытым диалогом

Удаление составного владельца снимает блокировку страницы, исключает диалог из stack/registry и сбрасывает временное состояние открытия. При повторном подключении окно не открывается самостоятельно. Снятие управляющего open-атрибута инвалидирует отрисовку, даже если внутренний open state уже false; иначе запоздавший render может оставить блокирующий overlay.

Локальная проверка после обеих правок: [Chromium](foundation-table-modal-attribute-chromium.json), [Firefox](foundation-table-modal-attribute-firefox.json), [WebKit](foundation-table-modal-attribute-webkit.json). Реальный Safari и единый release gate этими проверками не заменены.

## Жизненный цикл составного владельца

Smart-наследник освобождает свои ресурсы в onDisconnected, сохраняя базовые действия: mounted=false, освобождение внешнего шаблона и событие disconnected. Если компонент владеет вынесенным за свой DOM меню, он очищает только свою область и не затрагивает соседний экземпляр. Отключение отменяет pending UI, но не стирает applied data. Повторное подключение не создаёт повторных обработчиков.

Исполняемый table-срез: [Chromium](foundation-table-lifecycle-chromium.json), [Firefox](foundation-table-lifecycle-firefox.json), [WebKit](foundation-table-lifecycle-webkit.json). Подтверждены portal isolation, remount и ровно одна очистка external-template resources на каждое удаление. Не переносить эти результаты на другие Smart-классы или открытый modal при удалении владельца без отдельной проверки.

## Черновик и действующее состояние составного фильтра

Ввод до «Применить» не меняет applied filter и не отправляет onFilterUpdate. «Сбросить» и закрытие фильтра снаружи отменяют текущий черновик; следующее открытие показывает применённое значение. Каждое применение передаёт один актуальный payload. Внутреннее переключение меню не приравнивается автоматически к отмене.

Локальная проверка text control: [Chromium](foundation-table-filter-after.json), [Firefox](foundation-table-filter-firefox-control.json), [WebKit](foundation-table-filter-webkit.json). Серверную загрузку выполняет приложение; эти тесты не доказывают запросы, сложные entity controls и lifecycle всей таблицы.

## Идентичность вложенных контролов при обычном обновлении

Изменение состояния без смены типа/экземпляра контрола не должно пересоздавать его DOM. Стабильный ключ строки недостаточен, если её содержимое при каждом render создаёт новый Node. Для локального кандидата sf-table идентичность вложенного Smart-элемента принадлежит Lit child part; меняются его props и listeners, а не сам элемент. Удалённые props/listeners не сохраняются. При удалении части освобождаются refs/listeners; повторное подключение не умножает обработчики.

Проверять нужно исходный DOM-объект: Tab/Option+Tab → Enter → Escape возвращает фокус на него, а повторные открытия остаются работоспособными. Программный focus() на заново созданную кнопку не является доказательством сохранения идентичности. При настоящей смене типа/вида замена DOM допустима, но перенос состояния и фокуса требует собственного сценария проверки.

Локальные результаты: [Chromium](foundation-table-keyboard-chromium.json), [Firefox](foundation-table-keyboard-firefox.json), [WebKit Option+Tab](foundation-table-keyboard-webkit-option.json). [Нативная контрольная страница](foundation-webkit-native-tab.json) подтверждает, что тестовый WebKit пропускает обычную HTML-кнопку при Tab, но достигает её при Option+Tab; системные настройки не менялись. Эти результаты не заменяют настоящий Safari, полный composite-контракт и release metadata gate.

## Текущая интеграционная проверка полей

Core и Smart пересобраны из текущего source (`core-fields-product`, `smart-fields-product`), диагностика обоих пуста. [Единый Chromium-сценарий](foundation-fields-product.json) через настоящий Loader подтвердил input и textarea roundtrip между видами, FormData/reset/программное value и три гонки загрузки шаблонов. Missing assets/page errors отсутствуют. [Повторный Smart build](foundation-smart-fields-repro.json) сравнивает все621файл; совпадение не является immutable-commit release proof. Остаются текущая связка в Firefox/WebKit, повторный Core build, остальные сценарии генерального плана и выпуск.

Текущая связка также прошла [Firefox](foundation-fields-product-firefox.json) и [WebKit](foundation-fields-product-webkit.json): оба поля, roundtrip, textarea reset/FormData/controlled value и три гонки, errors[]. Повторный Core build запущен отдельно; его результат не выводится из браузерного PASS. Следующий предметный сценарий — существующий sf-table (его guide находится в src/smart/table/docs/smart-table-guide.md) с реальным фильтром и sf-modal; ни эти компоненты, ни настоящий Safari данным набором не приняты.

## Открытый разрыв: наблюдение template у полей

Уточнение form-среза: [Firefox](foundation-form-view-value-firefox.json) и [WebKit](foundation-form-view-value-webkit.json) подтвердили roundtrip input, reset и программное value. У textarea отдельный [браузерный тест до исправления](foundation-textarea-view-before.json) воспроизвёл пустое значение вместо двух введённых строк. В source SfTextarea.templateContext теперь использует текущий native textarea.value при отсутствии управляющего value-атрибута; прежний смысл явного value не меняется. Unit-регрессия до исправления падает; после исправления требуется продуктовая браузерная проверка. Не переносить PASS input на textarea.

Следующий срез устранил подтверждённую потерю значения: после восстановления template observation браузер показал пустой внешний input вместо «Документация!». В SfInput.templateContext uncontrolled value теперь читается из текущего native input, а при первом render — из defaultValue. Controlled value продолжает поступать из props. Встроенный uncontrolled template задаёт текущий value отдельно от reset defaultValue. Атрибут value не создаётся автоматически из пользовательского ввода.

Полная source suite179/179. Новая продуктовая Smart-сборка (`smart-value-product`) status0/diagnostics[]. [Браузерный результат](foundation-form-view-value.json) в Chromium через Loader: данные сохраняются в обе стороны, native reset возвращает исходное пустое значение, программное value доходит до внешнего вида. Это ещё не проверка textarea, IME, серверной отправки или полноценной доступности произвольного пользовательского шаблона. Core в этом испытании остаётся race-product, поэтому финальная единая связка после template-observation ещё требует пересборки и проверки.

Исправление в source candidate: template добавлен к общим observedAttributes, независимо от props конкретного компонента. Новый тест до исправления воспроизводит пропуск, после исправления оба теста проходят (включая отсутствие дубля при явном template prop); полная source suite175/175. Браузерная приёмка этого изменения ещё не получена. Попытка расширить лёгкий webpack fixture полем остановилась на отсутствующей обработке CSS imports; это ошибка тестовой сборки, не отказ поля. Дальше используется штатная продуктовая Smart-сборка.

В продуктовой проверке `--form --form-view` ввод и стандартное поведение sf-input проходят, но смена template на внешний вид не приводит к его появлению. [Отчёт](foundation-form-view-before.json) — pass=false, таймаут ожидания внешнего input, page errors отсутствуют. Первая попытка также содержала ошибочный путь fixtures `inputs` вместо tag-derived `input`; после исправления пути и завершения прежнего процесса отказ повторился. Не приписывать первую ошибку продукту.

Source объясняет отказ: базовый `observedAttributes` объединяет props и root-class/root-style/style, но не общий template. SfInput.props не содержит template; у ранее проверенного list-item контракт другой. Следующий шаг — регрессия общего наблюдения template, совместимое исправление base и затем проверка сохранения пользовательского значения в обе стороны. Потеря данных пока не доказана: сценарий остановился раньше.

## Последнее исправление: запоздавший импорт

9 сентября: три unit-регрессии на настоящем методе `resolveTemplateResult` воспроизвели позднее присвоение устаревшего внешнего модуля после смены вида, возврата к default и disconnect. Внешний `renderToken` guard защищал DOM, но не предшествовавшие ему изменение владельца и вызов кода шаблона.

В изолированном source candidate добавлена проверка mounted/renderToken/templateName сразу после ожидания импорта и до изменения владельца. Устаревший результат не вызывает render-функцию и не освобождает новый активный вид. До исправления: 0/3; после: 3/3, вместе с прежними lifecycle/update тестами 8/8. Это unit-проверки с управляемыми promises, ещё не сетевой браузерный сценарий. Прежние Core/Smart сборки не содержат это новое исправление и требуют обновления перед итоговой приёмкой.

Следующая проверка выполнена с настоящей асинхронной загрузкой модулей в браузере: route-перехватчик удерживает запрос старого шаблона, компонент переключается на новый/default либо удаляется, после чего запрос отпускается. [Chromium](foundation-template-race-browser.json), [Firefox](foundation-template-race-firefox.json) и [WebKit](foundation-template-race-webkit.json) проходят все три случая. [Прежняя продуктовая сборка](foundation-template-race-before.json) тем же тестом отклонена: активным владельцем становится race-slow-fast вместо race-fast. Это отрицательный контроль, не случайный сетевой отказ.

Текущий source собран отдельным webpack fixture, не полной продуктовой сборкой; тест без Core Loader. WebKit не означает приёмку Safari. Полная source suite: 173/173. Следующий шаг — пересборка Core/Smart и повторение сценария на точных продуктовых файлах через Loader.

Продуктовая проверка следующего среза: Core и Smart пересобраны с пустой диагностикой, [сценарий через настоящий Loader](foundation-template-race-product.json) прошёл в Chromium с strict candidate roots (без baseline fallback). Все три задержанных запроса проверены; отсутствующих ассетов и page errors нет. [Повторная Smart-сборка](foundation-smart-race-repro.json): 621 файл побайтно совпадает. Это ещё не immutable-commit release и не полный browser/consumer набор. Повторная Core-сборка на момент записи ещё выполняется.

Завершающий readback этого среза: [Core reproducibility](foundation-core-race-repro.json) — 59 файлов идентичны, диагностика пустая. Продуктовый сценарий через Loader также прошёл в [Firefox](foundation-template-race-product-firefox.json) и [WebKit](foundation-template-race-product-webkit.json): в каждом три гонки, 18 запросов к явно указанным candidate roots, errors/missingAssets — пустые. Все процессы завершены. Это закрывает выбранную гонку импорта; не заменяет сценарии формы, composite, настоящего Safari и старого потребителя.

Статус: рабочая фиксация существующего поведения и открытых требований фундамента, не новый принятый API. Источник — `ui-loader/src/cl/classes/template/sfBaseElement.js` и `src/smart/list-item/`; [проверка](foundation-template-proof.json), [исполняемый сценарий](check-foundation-container.mjs).

## Что уже существует

Компонент владеет props, нормализацией атрибутов, обновлением и жизненным циклом. `template="default"` выбирает встроенный вид. Иное имя разрешается в модуль `base/component/template/index.js`; базовый путь может задаваться `SF_SMART_TEMPLATE_PATH`, иначе используется `/local/smart/templates`. Это существующая адресация, не новый registry, который ещё нужно создать.

Модуль экспортирует default-функцию, получающую `html`, `nothing`, `context`, `component`, `changedAttributes`. Необязательный `mapContext` преобразует контекст. CSS ищется рядом как `index.css`. При отсутствующем или неимпортируемом модуле код возвращается к встроенному шаблону. Runtime fallback найден в исходнике, но отказ сети этим браузерным сценарием не испытан.

Шаблон отвечает за отображение props, DOM, роли, ARIA и работу элементов управления. Передача `disabled` в context сама по себе не делает произвольный HTML недоступным для взаимодействия. Поддержка слотов требует явного использования штатных slot API. Пример использует существующий trailing slot без дублирования его данных.

## Что доказано

В Chromium151 выполнена цепочка: стандартный list-item → внешний модуль с другой DOM-структурой → изменение text/selected/disabled → detach/attach → возврат к default. Значения и слот сохранены; повторный mount проверен последовательностью `sf-disconnected`, `sf-connected`, `sf-after-render`, а не только наличием старого DOM. Для disabled проверен tabindex=-1 и aria-disabled=true.

Код эксперимента собирается отдельно из настоящего исходника Smart. Это не полный продуктовый build и не приёмка всех Smart. Клавиатурная активация, действие, перенос фокуса, ошибки, несколько экземпляров с конкурентным импортом, Firefox/Safari и смена на другой внешний шаблон пока не покрыты.

## Исправленная граница частичного обновления

`performComponentUpdate` сначала вызывает component-specific `resolveUpdateMode`/`updateDom`. У list-item оптимизированное обновление ищет стандартные CSS-классы. Если внешний вид полностью меняет DOM, updateDom возвращает false и выполняется полный render — это подтверждено.

Внешний вид может сохранить часть стандартных CSS-классов и вывести те же props ещё в другом месте. [Регрессия воспроизведена](foundation-template-shared-before.json): основной текст изменился, второе отображение осталось старым. Это не теоретический риск.

В source candidate `performComponentUpdate` теперь разрешает component-specific DOM-оптимизацию только встроенному виду, когда внешний модуль не активен. Внешний шаблон обновляется через свой render; при возврате к default тоже выполняется render, после чего стандартная оптимизация снова доступна. Новый публичный API не вводится.

[После исправления](foundation-template-shared-after.json) оба отображения обновляются; selected/disabled, слот, повторное подключение и возврат к default проходят. Три unit tests дополнительно проверяют сохранение стандартного fast path, его fallback и переключение с внешнего вида. Это проверка source candidate через изолированную сборку, ещё не опубликованное исправление. Повторный Lit render не означает обязательного пересоздания всего DOM; сохранение фокуса и ресурсов конкретных шаблонов требует отдельных проверок.

## Инварианты для дальнейшего приёмочного набора

### Очистка внешнего вида

[До исправления](foundation-template-cleanup-before.json) после external→default сохранялась одна активная запись ресурса в проверочном шаблоне: destroy вызывался при disconnect, но не при смене вида. [После исправления](foundation-template-cleanup-after.json) запись освобождается. Проверка использует контролируемый учёт владельцев через WeakSet и счётчик, не измеряет память браузера или реальные сетевые подписки.

В candidate добавлено идемпотентное освобождение текущего внешнего модуля перед заменой и в finally базового disconnectedCallback. Владение очищается до пользовательского hook, поэтому повторный вход не вызывает destroy дважды. Переопределение onDisconnected без super больше не пропускает эту базовую очистку. Существующий вызов super остаётся совместимым. Пять unit tests подтверждают обновления, идемпотентность и finally при исключении обработчика; браузер проверяет повторный mount и смену вида.

Сам destroy обязан освободить ресурсы конкретного шаблона. Runtime не может автоматически угадать подписки пользовательского кода. Асинхронные гонки загрузки разных views, фокус и реальные формы пока не приняты этим испытанием.

- При смене вида пользовательские данные и объявленные props не теряются.
- Внешний вид не обязан повторять приватную DOM-структуру встроенного.
- Состояние, доступность и действия проверяются отдельно от геометрии.
- Внешние модули — доверенный код проекта, не произвольный исполняемый код из пользовательского контента.
- Освобождение ресурсов внешнего вида проверяется на смене вида и отключении элемента; наличие destroy hook не является доказательством всех путей очистки.
- Документация различает работающий контракт, требования совместимости автора шаблона и ещё не испытанные сценарии.
