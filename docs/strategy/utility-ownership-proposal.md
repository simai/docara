# Владение utility-селекторами и совместимость модулей

Статус: предложение, runtime не изменён. Основание — [сверка640CSS-модулей](foundation-utility-overlap.json).

## Инварианты

- Публичный класс имеет одно каноническое назначение и один канонический модуль загрузки.
- Совместимый модуль может сохранять прежний URL/CSS, но его соответствие каноническому модулю должно быть явным, проверяемым и ацикличным.
- Ни совпадение имени, ни похожий CSS не дают Loader права произвольно пропустить модуль.
- Для alias проверяется не только имя селектора: значения, important, слой, условия и зависимости должны покрываться каноническим модулем. Самостоятельное старое подключение CSS продолжает работать.
- CSS↔Loader аудит проверяет собственный модуль либо его явно объявленное эквивалентное разрешение; исключений по строковым именам в тестах не добавлять.

## col-gap

Рекомендуемый владелец — существующий gap-пакет: он уже содержит gap, row-gap, col-gap и совместимые g/g-x/g-y/gap-x/gap-y. Для пяти column-gap модулей сохраняются CSS по прежним адресам; новая автоматическая загрузка разрешает их в соответствующий gap-модуль через явный alias manifest. Поэтому old explicit CSS и новый Loader сохраняют результат без двух запросов.

До реализации проверить все declarations/условия, а не только один md пример. После реализации проверить отдельно col-gap как единственный класс, gap+col-gap, динамическое добавление, responsive, старый прямой CSS и запросы сети. Alias metadata должна иметь одного source owner в ui-loader, обрабатываться builder и Loader, а не вручную дописываться в ui. Текущий Loader не имеет подтверждённого такого контракта — нельзя изображать его уже существующим.

## .table

Это не alias: display и оформление выполняют разные задачи. Текущая документация обещает чистый display, но фактическая автозагрузка добавляет оформление. Пока сохранить прежнюю .table как legacy composition; не менять смысл молча и не делать table-модуль alias к display.

Предлагаемый добавочный чистый класс — display-table со значением display:table, включая существующие viewport формы. Остальные display-классы не переименовывать. В документации .table явно помечается как совместимое совмещённое поведение; новое оформление таблиц должно иметь компонентное имя, выбранное после сверки Smart/компонентных контрактов. Не объявлять несуществующий sf-table CSS-компонент и не смешивать его с тегом sf-table Smart.

Это предложение нового имени; оно требует принятия до изменения публичной документации и генерации. Альтернатива — оставить .table совмещённой и документировать ограничение без нового имени; тогда универсальная чистая table-display утилита остаётся пробелом.

## Приёмка

Старые классы/URL не ломаются; col-gap даёт один автоматический модуль, direct legacy CSS работает; display-table не подключает оформление таблицы; нет alias циклов/непокрытых declarations; exact whole-class matching и отрицательные тесты сохраняются; generated registry, CSS, документы и consumer lock отражают один контракт.
